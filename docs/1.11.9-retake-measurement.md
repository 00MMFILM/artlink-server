# 1.11.9 재촬영 측정 계약

2026-09-27. 구현 기준: 서버 `2709d6a` + 재촬영 이벤트 허용 목록 패치. 아래 SQL은 검토용이며 운영 DB에서 실행하지 않았다. 스키마·기존 대시보드·요금 정책은 바꾸지 않는다.

## 이번 이벤트의 의미

`retake_capture_added`, `retake_analysis_done`, `compare_viewed`, `resume_card_tapped`는 기존 `funnel_events`에 저장한다. `(device_id, event)` 중복을 무시하므로 각 단계에 처음 도달한 **기기 수**를 확인하는 용도다. 반복 분석 횟수, 이용자 수, 결제자 수가 아니다. `retake_analysis_done`은 앱이 분석 성공을 확인한 시점에만 전송해야 한다. 서버 변경을 앱보다 먼저 배포해야 새 이벤트가 400으로 버려지지 않는다.

## 기존 보고서와 구별할 점

- `api/_practiceStats.js`의 7일 재방문은 장면과 관계없는 서로 다른 세션을 센다. `subject_key`를 조회하지 않으며 `checkin`도 포함한다. 이번에 이 정의를 바꾸지 않았다.
- `schema-practice-events.sql`의 예전 같은 장면 view도 영상·AI 성공·서로 다른 세션 조건을 모두 보장하지 않는다. 새 기능의 분석 성공 지표로 그대로 사용하지 않는다.
- `practice_completed(kind=video)`는 영상이 첨부된 노트의 **저장**이다. 분석하지 않고 저장한 경우도 있어, 이것만 2건이라고 분석이 2회 성공한 것은 아니다.
- 첫 분석 시 `ai_feedback_done.subject_key`는 아직 `null`일 수 있다. 저장 뒤에 노트 ID가 생긴다. 따라서 `(device_id, auth_user_id, session_id)`로 분석 성공 이벤트와 저장 완료를 연결하고, 장면은 완료 이벤트의 `subject_key`를 사용한다.
- 재촬영 체인의 장면 키는 `sceneId > rootNoteId > parentNoteId` 순서다. ACT RAW 장면은 장면 ID, 일반 노트는 최초 노트 ID가 기준이다. `COUNT(DISTINCT session_id)`로 같은 세션의 중복 이벤트를 제거한다.

## 읽기 전용 SQL 예시

최근 30일 안에 **분석 성공 후 저장까지 완료한** 영상 세션을 찾고, 같은 기기·계정·장면에서 2개 이상의 서로 다른 세션이 있는지 센다. 체크인·텍스트·단순 재분석(`reanalysis`)은 제외한다. 시험 기기 ID는 `excluded_device_ids`에 운영자가 지정한다. 빈 배열이면 시험 기기도 포함되므로 결과를 실사용 지표로 확정하지 않는다.

```sql
WITH params AS (
  SELECT NOW() AS until_at,
         NOW() - INTERVAL '30 days' AS since_at,
         ARRAY[]::text[] AS excluded_device_ids
), completed AS (
  SELECT p.device_id, p.auth_user_id, p.session_id,
         MAX(p.subject_key) AS subject_key,
         MIN(p.occurred_at) AS completed_at
  FROM practice_events p
  CROSS JOIN params cfg
  WHERE p.event = 'practice_completed'
    AND p.kind = 'video'
    AND NULLIF(BTRIM(p.subject_key), '') IS NOT NULL
    AND p.occurred_at >= cfg.since_at
    AND p.occurred_at < cfg.until_at
    AND (p.received_at IS NULL OR
         (p.received_at <= cfg.until_at AND
          p.occurred_at <= p.received_at + INTERVAL '10 minutes'))
    AND NOT (p.device_id = ANY(cfg.excluded_device_ids))
  GROUP BY p.device_id, p.auth_user_id, p.session_id
  -- 한 세션에 모순되는 장면 ID가 실렸다면 추측해 묶지 않는다.
  HAVING COUNT(DISTINCT p.subject_key) = 1
), analyzed_and_saved AS (
  SELECT c.*
  FROM completed c
  WHERE EXISTS (
    SELECT 1
    FROM practice_events f
    CROSS JOIN params cfg
    WHERE f.device_id = c.device_id
      AND f.auth_user_id IS NOT DISTINCT FROM c.auth_user_id
      AND f.session_id = c.session_id
      AND f.event = 'ai_feedback_done'
      AND f.kind = 'video'
      AND f.occurred_at <= c.completed_at
      AND (f.received_at IS NULL OR
           (f.received_at <= cfg.until_at AND
            f.occurred_at <= f.received_at + INTERVAL '10 minutes'))
  )
), subjects AS (
  SELECT device_id, auth_user_id, subject_key,
         COUNT(DISTINCT session_id) AS analyzed_sessions
  FROM analyzed_and_saved
  GROUP BY device_id, auth_user_id, subject_key
)
SELECT
  (SELECT COUNT(*) FROM analyzed_and_saved) AS analyzed_and_saved_sessions,
  COUNT(*) FILTER (WHERE analyzed_sessions >= 2) AS subjects_with_two_sessions,
  COUNT(DISTINCT device_id) FILTER (WHERE analyzed_sessions >= 2)
    AS devices_with_two_sessions,
  (SELECT CARDINALITY(excluded_device_ids) FROM params) AS excluded_test_devices
FROM subjects;
```

이 SQL의 한계:

- 같은 기기에서 게스트 → 가입으로 바뀐 사이클을 같은 사람이라고 추정하지 않는다. 계정이 일치하는 이벤트만 연결하므로 가입 전후에 걸친 연습을 적게 셀 수 있다. 여러 기기도 합치지 않는다.
- 30일 구간 밖의 첫 연습은 분모에 포함되지 않는다. 7일 재방문율이나 설치 대비 전환율을 계산하는 SQL이 아니다.
- 분석 성공 후 저장하지 않은 노트, 오프라인 큐가 아직 전송되지 않은 노트는 빠진다. 최초 도달은 `retake_analysis_done`, 저장된 반복은 이 쿼리로 각각 관찰한다.
- `ai_feedback_done`은 앱의 성공 이벤트다. 서버의 유료 AI 사용 기록이나 결제 내역과 대조한 감사 수치가 아니다.
- `subject_key`가 같은 ACT RAW 장면이면 독립적으로 작성한 노트도 같은 장면 연습으로 묶인다. 정확한 부모·자식 노트 체인 개수와는 다르다.
- 실제 촬영한 새 영상인지 파일 내용까지 검사하는 계측은 없다. 같은 파일을 다시 골라도 새 세션이라면 집계된다.
